As of 2026-11-13. Not legal advice; counsel should review any place before software reads it at volume.

All pages below were fetched on 2026-11-13 unless noted. "Live check" means I sent one request to the endpoint on that date and got a valid response. I did not log in, create accounts or submit forms, and I never requested linkedin.com, licdn.com or lnkd.in. Section B was gathered by a delegated agent using WebFetch, which summarises pages; its quoted sentences are that tool's extraction and should be re-read on the vendor page before any contract.

### Legal position of scraping a search engine

Google's own post (https://blog.google/technology/safety-security/serpapi-lawsuit/, dated December 19, 2025) says Google filed suit against SerpApi that day. It alleges SerpApi circumvents "security measures protecting others' copyrighted content" using concealment, high-volume bot traffic and rotating crawler identities, and resells licensed content. Secondary reporting (WebSearch, not primary) says the case is in the Northern District of California, pleads DMCA section 1201 anti-circumvention, and went through a motion to dismiss with leave to amend. I could not confirm the docket. I found no primary statement that scraping a search engine is lawful. Use a licensed search API instead.

## C. Rules for a polite fetcher

Source for all RFC statements: https://www.rfc-editor.org/rfc/rfc9309.txt (fetched 2026-11-13).

The partner decided on 2026-11-13 that this system does not obey robots.txt. The notes below record what the RFC says. They are not the reader's rules.

Implement these:

1. **Fetch `/robots.txt` first, per host.** The file is at `scheme://authority/robots.txt`, UTF-8, `text/plain`. "These rules are not a form of access authorization." A hostname that is not the site (for example `api.example.com`) has its own file.
2. **Status handling.** 2xx: follow the rules. Redirects: follow at least five, even across hosts, and apply the rules to the original authority. 4xx ("unavailable"): "the crawler MAY access any resources on the server." 5xx or network failure ("unreachable"): "the crawler MUST assume complete disallow". After a long period of undefined status (example: 30 days) you may treat it as unavailable or keep a cached copy.
3. **Cache at most 24 hours** unless the file is unreachable ("SHOULD NOT use the cached version for more than 24 hours").
4. **Parse at least 500 KiB.** "The parsing limit MUST be at least 500 kibibytes." Treat the file as untrusted text.
5. **User-agent matching.** Pick a product token of letters, underscore and hyphen only, and make it a substring of your `User-Agent` header. Match group names case-insensitively. If several groups match, merge their rules. If none match, use the `*` group. If neither exists, no rules apply. The header should describe the purpose and give a contact URL.
6. **Rule matching.** Case-sensitive path match from the first octet. "The most specific match found MUST be used", meaning the rule with the most octets. On a tie "the 'allow' rule SHOULD be used". `/robots.txt` is implicitly allowed. Support `*` (any run of characters), `$` (end anchor) and `#` (comment). Percent-encode non-ASCII octets before comparing. Ignore rules that appear before the first `user-agent` line.
7. **`Crawl-delay` is not in RFC 9309** (the string does not occur in the text I fetched). It is a vendor extension that real sites use: Hacker News sets `Crawl-delay: 30`, arXiv `15`, X `1`. Common Crawl says "We obey the Crawl-delay parameter". Honour it when present as a minimum gap between requests to that host, and apply your own default of at least one request per second per host when absent. Back off on HTTP 429 and 5xx, and honour `Retry-After`. Respect published API limits: SEC 10 per second, arXiv one per three seconds.
8. **Sitemaps** are an optional record and "MUST NOT terminate a group".
9. **Robots rules are not the whole contract.** Terms of service can forbid what robots.txt allows (Devpost, Substack, YC all allow `*` in robots.txt while their terms bar scraping). Check both.

AI-agent conventions, none of them binding:

- **Named AI user agents.** Sites now list AI crawlers by name under `Disallow: /`. Indie Hackers lists `anthropic-ai`, `ClaudeBot`, `Claude-SearchBot`, `GPTBot`, `PerplexityBot`, `meta-externalagent`, `OAI-SearchBot`, `YouBot` and others; mastodon.social lists `ClaudeBot`, `anthropic-ai`, `GPTBot`, `CCBot`, `Meta-ExternalAgent`. A fetcher must send its own distinct product token (never `*` alone, never a browser string) so that such a rule can match it and so that owners can allow or deny it by name.
- **Web Bot Auth.** Cloudflare documents it as "an authentication method that leverages cryptographic signatures in HTTP messages to verify that a request comes from an automated bot", built on RFC 9421 (HTTP Message Signatures, published February 2024) and two IETF drafts: a key directory and a protocol (https://developers.cloudflare.com/bots/concepts/bot/verified-bots/web-bot-auth/). The architecture draft I fetched, `draft-meunier-web-bot-auth-architecture-05`, is marked "Replaced" and "Expired & archived". It is optional for a fetcher and only matters if you want to be verified by sites that use Cloudflare. Cloudflare also lists "obeys robots.txt and crawl directives" as a verification criterion.
- **AI preferences.** `draft-ietf-aipref-vocab-08` (14 September 2026, Internet-Draft, not a standard) defines "a vocabulary for expressing preferences regarding how digital assets are used by automated processing systems". A companion draft covers attaching preferences to content. Parse them if you can; treat a denial as a stop.
- **llms.txt** is a proposal (llmstxt.org) for a Markdown file that tells models where to read. It is a hint for content discovery, not an access control, and the page defines no deny semantics.

## D. Evidence on timing

Short. The published evidence supports a lead of up to a year for GitHub activity and nothing firmer for the other places.

- **GitHub.** Roche's working paper links 160,065 US startups from Crunchbase to GitHub accounts. Its abstract: "startups accelerate their activities on the platform in the twelve months prior to raising their first financing round. The intensity of their involvement on GitHub declines in the twelve months after." The published version is Conti, Peukert and Roche, Organization Science 2025 (reported by a search snippet: engagement with external open-source repositories raises the odds of funding by at least 36%). Source fetched: https://www.hks.harvard.edu/centers/mrcbg/programs/growthpolicy/beefing-it-your-investor-open-sourcing-and-startup-funding. This measures startups that already exist in Crunchbase, so it does not say how early an individual before incorporation can be seen.
- **Short lead claims are not supported.** A Hugging Face and Mendeley dataset of about 55 startups hypothesises 6 to 12 weeks, and says it is for exploratory use, not causal claims (WebSearch snippet). Blog claims of 3 to 6 weeks gave no checkable backtest. I did not rely on them.
- **Form D.** Filing is due 15 calendar days after the first sale, which is when the first investor is irrevocably committed; filing before the first sale is allowed (law-firm summaries from WebSearch, not the SEC rule text). It therefore marks a raise in progress, not an early signal. I found no study of how long before a Form D a founder appears elsewhere.
- **Founder departures, Show HN, domain registration, package publication:** I found no published study of lead time to funding or launch. There is none to cite.

## Off limits

Quoted sentence for each. "Off limits" means these words forbid or bar automated access for this use, or access needs an agreement we do not have.

- **Devpost:** "Uses manual or automated software, devices, scripts robots, or other means or processes to access, 'scrape,' 'crawl' or 'spider' the Site, User Content (including User Profiles and Team Pages), or any related data or information" (Terms of Use, https://info.devpost.com/terms).
- **Y Combinator website:** "In connection with your use of the Site you will not engage in or use any data mining, robots, scraping or similar data gathering or extraction methods." (https://www.ycombinator.com/legal/)
- **Product Hunt API:** "The Product Hunt API must not be used for commercial purposes. If you would like to use it for your business, please contact us at hello@producthunt.com." (https://api.producthunt.com/v2/docs)
- **Substack pages:** a user may not do any process that "'Crawls,' 'scrapes,' or 'spiders' any page, data, or portion of Substack (through use of manual or automated means)" (https://substack.com/tos).
- **Reddit:** `robots.txt` has `User-agent: *` / `Disallow: /` (https://www.reddit.com/robots.txt).
- **Indie Hackers for AI agents:** robots.txt lists the named AI user agents above with `Disallow: /` (https://www.indiehackers.com/robots.txt). Its terms returned 403, so the human-browser rule is unread.
- **GitHub, for outreach lists:** "You may not use information from the Service ... for spamming purposes, including for the purposes of sending unsolicited emails to users or selling personal information, such as to recruiters, headhunters, and job boards." This does not bar reading the API; it bars those uses of what you read. (https://docs.github.com/en/site-policy/acceptable-use-policies/github-acceptable-use-policies)
- **X:** not forbidden but paid and redistribution-limited: developers may give each user "up to 500 public Posts Objects and/or User Objects" per day "via non-automated means" (X developer terms).

Professional-network sites remain out of bounds per the existing note and were not touched.
